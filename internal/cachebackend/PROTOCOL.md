# GitHub cache service v2 API

This Go client calls GitHub's cache service v2 API directly. The service version is independent of the `actions/cache` action's release version, such as `actions/cache@v6`; this client does not invoke that action.

This package implements the results service, not the legacy `_apis/artifactcache` API. Protocol references checked on 2026-11-07:

- [Toolkit generated Twirp client](https://github.com/actions/toolkit/blob/main/packages/cache/src/generated/results/api/v1/cache.twirp-client.ts): service methods and snake_case JSON encoding.
- [Toolkit generated cache messages](https://github.com/actions/toolkit/blob/main/packages/cache/src/generated/results/api/v1/cache.ts): lookup, reservation, and finalization fields; `size_bytes` is a decimal JSON string.
- [Toolkit results HTTP client](https://github.com/actions/toolkit/blob/main/packages/cache/src/internal/shared/cacheTwirpClient.ts): origin-relative `/twirp/github.actions.results.api.v1.CacheService/` methods and runtime bearer authentication.
- [Toolkit cache lifecycle](https://github.com/actions/toolkit/blob/main/packages/cache/src/cache.ts) and [upload helper](https://github.com/actions/toolkit/blob/main/packages/cache/src/internal/uploadUtils.ts): signed Azure Blob URLs, upload before finalization, reservation/finalization `ok` responses.
- Microsoft [Put Blob](https://learn.microsoft.com/en-us/rest/api/storageservices/put-blob), [Put Block](https://learn.microsoft.com/en-us/rest/api/storageservices/put-block), and [Put Block List](https://learn.microsoft.com/en-us/rest/api/storageservices/put-block-list): direct and staged blob transfers, fixed-length base64 IDs, ordered block commit.

The runtime token authenticates only control requests. Signed URLs authenticate blob requests without an Authorization header. Redirects are refused for both, including with a supplied HTTP client. Error messages contain operation names, numeric HTTP status codes and fixed transport categories. Typed timeout, DNS, TLS verification/record and connection failures receive allowlisted text; unknown failures remain generic. Classification never matches arbitrary error strings. Raw transport causes are discarded rather than wrapped, including their URLs, hostnames, certificate details and proxy configuration. Only safe category identities and cancellation/deadline identities remain available to callers. Remote messages, request URLs and JSON parse errors are deliberately excluded. `Entry.URL` remains a credential and must never be logged or persisted.

The default compressed transfer ceiling is 10 GiB. `Client.MaxBytes`, `BlockSize`, and `Concurrency` permit explicit tuning, with validation. Small uploads use one Put Blob request. Larger uploads stream 32 MiB blocks through four workers, without allocating block-sized buffers; a mutex adapter supports generic seekable sources. The default transfer settings are implementation choices awaiting measurements, not performance claims. Operations time out, and caller cancellation propagates. Uncommitted remote blobs from interrupted uploads rely on service expiry; entries are never finalized after transfer failures.

Replay-safe requests have at most three application-level attempts: lookup POST, archive/range GET and deterministic Azure Put Blob, Put Block and Put Block List operations. Retries cover HTTP 408/429/500/502/503/504 and transient connection errors before a successful response is consumed. Backoff is jittered (250–500ms, then 500–1000ms); a larger `Retry-After` delay is honored up to five seconds per retry. Caller deadlines and cancellation bound the entire operation, including delays. Redirects, authentication/permission failures, invalid requests, malformed JSON, content-range/length errors and archive/checksum failures are not retried. No response-body read is replayed after partial consumption, including generic download writers.

Reservation and finalization remain single-attempt even on transient HTTP status or ambiguous transport failures. Repeating either cannot prove that the original service operation failed. Payload PUT retries use independent bounded section readers over the same bytes and block IDs. Block-list requests use the same ordered `Latest` IDs, which resolve either uncommitted or already committed blocks on a replay; see Microsoft's [Put Block](https://learn.microsoft.com/en-us/rest/api/storageservices/put-block) and [Put Block List](https://learn.microsoft.com/en-us/rest/api/storageservices/put-block-list) contracts. This assumes the action exclusively owns its fresh reservation and does not mutate its source while uploading. Runtime tokens remain confined to the control endpoint on every attempt. Progress counts successful payload acknowledgements once; retransmitted failed upload attempts are additional network work and are not included in the successful-payload report. This local policy has not been validated against hosted transient failures or measured for availability/latency improvements.

Whole-archive downloads to files use independent `DownloadConcurrency` and `DownloadBlockSize` controls (four workers / 32 MiB by default). The first range response establishes size before subsequent bounded workers write validated offsets. Content-Range, total/part lengths and untransformed content are validated; a supplied strong ETag pins subsequent requests. A full 200 response to the initial range is consumed directly without a duplicate download. Generic writers and concurrency 1 retain single-GET streaming. Empty-object range rejection falls back to a full GET. Workers cancel and join before returning errors. Local range/fallback/invalid-response/cancellation fixtures pass; hosted range behavior remains unverified until the user tries the preview.

`ErrConflict` identifies HTTP 409 and Twirp `already_exists`. `ErrPermission` identifies HTTP 401/403, permission Twirp codes, and the current toolkit's explicit write-policy denial prefix. Other `ok:false` reservation/finalization replies remain generic refusals: they are not assumed to prove contention. A lookup `ok:false` is a miss. Branch and default-branch visibility belong to the service and token scopes.

Local httptest coverage verifies JSON requests, separate blob authentication, direct/parallel uploads, commit order, generic seekable readers, limits and truncation, service failures, denied access, redirects, cancellation, and secret-safe errors. These simulations do not establish live service compatibility, cross-platform behavior, throughput, or branch-scope semantics. The initial Linux/amd64 archive cold-save and warm-restore/post-save path passed on 2026-11-09; other hosted cases still require authorization. See development status for exact runs and limits.

## Optional chunked snapshot layer

The Go cache lifecycle can store content-defined chunk blobs plus a fresh JSON manifest through this same backend. Chunks use a separate version identity from manifests and exact finalized lookups; no prefix match or conflicting reservation proves chunk availability. References contain bounded lower-case SHA-256 digests and sizes, never URLs. Chunk keys are derived locally within the snapshot compatibility namespace. Encoded chunk checksums, aggregate sizes and complete tar validation are checked before publishing local files. Missing referenced entries are cache misses; the service may evict chunks independently of manifests. There is no additional storage service or chunk-deletion API. This is application-level reuse, distinct from the backend's multipart upload blocks.

Chunked snapshots use a separate independently bounded worker pool (default four, 1-16). The cache client is copied for chunk operations with blob-block upload and range-download concurrency set to one, retaining the caller's HTTP client, timeout/security behavior, block size and byte limits. This prevents nested request concurrency from multiplying worker settings. Duplicate chunk requests within one snapshot are suppressed; exact finalized lookup is still required after reservation conflict. Worker cancellation is propagated and joined before manifest publication or private-file cleanup.

Cache service version identities use complete 64-character SHA-256 hex digests, matching the toolkit cache-version generator; shortened digests are reserved for key namespace components. The initial hosted smoke rejected the earlier 24-character versions with HTTP 400; the corrected preview passed the Linux cold and warm hosted runs recorded in development status. Errors can include the fixed operation name and allowlisted `invalid_argument` code, never arbitrary remote messages or codes.
