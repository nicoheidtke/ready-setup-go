# Architecture and resource behavior

The root action uses GitHub's Node 24 runtime for credentials and automatic post-job hooks. Minimal, dependency-free launcher glue asynchronously invokes a precompiled Go executable without a shell, forwards SIGINT/SIGTERM, and waits for its exit; installation, cache policy, archive handling and service networking stay in Go. An optional lightweight distribution uses a Node bootstrap to acquire the Go executable. Consumers do not install npm packages or build the action. The default bundled distribution contains six executables, so action acquisition transfers binaries for platforms the current job does not use. Lightweight distributions omit those binaries and pin a `NATIVE_DOWNLOADS.json` manifest alongside the launcher. The bootstrap selects one OS/architecture, streams its public GitHub release asset into private runner temporary storage, verifies the exact size and SHA-256, then atomically publishes a digest-keyed executable. Main, post, and the Node alias rehash and reuse that file; existing invalid files cause failure rather than replacement.

The `experimental/node` path aliases the root lifecycle. The Bash composite at `experimental/composite` installs Go only and exists for launcher comparisons; it does not provide automatic caching. See [usage](USAGE.md) for the public interface, [development](DEVELOPMENT.md) for packaging and verification, the [security model](SECURITY_MODEL.md) for permissions and trust boundaries, and the [cache protocol](../internal/cachebackend/PROTOCOL.md) for service details.

Bootstrap requests send no credentials and follow at most five HTTPS redirects within GitHub and its asset CDNs. A two-minute deadline covers up to three attempts with bounded backoff for transient request/status failures; consumed-body, integrity and permission failures are not retried. The manifest caps each executable at 256 MiB. Payloads stream through bounded buffers rather than being retained whole. Cancellation interrupts acquisition and normal cleanup removes private partial files. Abrupt termination may leave private staging, as with other runner temporary data. A pinned manifest authenticates expected bytes; the release URL is a mutable locator whose deletion or replacement can still make acquisition unavailable. No controlled complete-workflow speedup has been established.

## Installation

Completed matching toolchains are discovered in the runner tool cache and the action's installation directory. Missing versions are resolved through official Go metadata, downloaded with SHA-256 and size verification, extracted privately and published with a directory rename. An interrupted install is never marked complete; existing installations are not overwritten.

New toolchains live under `RUNNER_TEMP/ready-setup-go/toolchains`. Linux/macOS tar archives stream through extraction. Windows ZIP archives require temporary storage for random access. Toolchain persistence depends on the runner; a warm dependency cache does not imply an installed compiler on a fresh runner.

Toolchain extraction accepts at most 100,000 file/directory entries and 4 GiB of expanded data. For tar, the byte budget includes headers, padding and trailing gzip members; ZIP budgets the cumulative expanded file payload and checks declared sizes before opening entries. These internal safety ceilings reject oversized archives, including otherwise checksum-valid ones, without changing version selection or installation paths. They bound expansion before publication, not total process memory or filesystem allocation; the standard ZIP reader parses its central directory before the entry-count check. Context checks cover download, archive traversal and file-copy reads, including ZIP extraction after download, and run again before marking/publishing an installation. Blocking filesystem calls may finish before cancellation is observed.

## Cache lifecycle and transfer

Enabled caching defaults to dependency baselines (`cache-save-policy: on-miss`) written only on the default branch (`cache-save-branches: default`). Branch eligibility uses the actual heads ref and repository/default-branch fields from a runner event object limited to 1 MiB; unavailable or inconsistent metadata intentionally denies saves. Main skips save registration on ineligible refs, and post rechecks eligibility and runner permissions before backend construction. The `all` branch policy permits GitHub-scoped branch/PR writers without changing keys or service visibility. Empty policy fields in compatible old main/post state retain legacy always/all behavior.

Only complete successful restoration establishes a dependency match in private main/post state. On-miss skips matching snapshots before any save-time root access, module fingerprinting, packing or upload. Compatible fallback still seeds a new dependency baseline. Restore omits the module content digest in this mode. Always mode retains module content checks and fresh build snapshots. Post needs no backend when all snapshots are already skipped. Snapshot prefixes, fresh immutable save keys, archive formats, job isolation and cache-hit output semantics remain unchanged.

Dependency discovery and hashing independently allow at most 10,000 unique selected files, 16 MiB of cumulative workspace-relative path bytes, and 1 GiB of aggregate file contents. Explicit selection text is limited to 1 MiB and 10,000 nonempty paths, including repeated selections; overlapping directories/files count once toward discovered-file budgets. File sizes are checked during discovery, and actual reads enforce the content ceiling if files grow afterward. Cancellation is checked during discovery and before and after each content read. Directory enumeration and blocking filesystem calls remain OS-controlled; these logical budgets are not a process-memory or latency guarantee. Accepted files retain the existing sorted name/content fingerprint and cache identities. Oversized selections fail cache preparation under the configured error policy; use narrower dependency paths for unusually large workspaces. These source changes require a newly packaged distribution.

Cache lookup and download can begin after exact version selection, overlapping toolchain installation. Destination paths still come from the selected Go executable. `cache-overlap: false` retains sequential operation. Overlap may retain both split downloads temporarily; sequential restore retains one archive at a time. Split downloads and merges themselves remain ordered rather than forming a transfer/merge pipeline.

Whole-archive downloads use bounded parallel HTTP ranges when the service supports them. A full response to the initial range request is consumed directly as a single-download fallback. Download workers and range sizes are independent of upload controls; concurrency 1 uses a single GET. Workers stream bounded buffers rather than retaining full ranges in memory, and cancellation joins workers before cleanup.

Restore validates the complete tar/compression stream in private staging before changing destination cache entries. Staging uses the destination filesystem where possible. On Windows, missing destination roots or subtrees are published with a same-volume directory move that atomically refuses existing destinations, including empty directories. File and directory metadata are finalized in private staging before the move. Existing trees, refused moves, other platforms and unsupported filesystems retain non-overwriting hard-link publication with an exclusive-create copy fallback. Windows tree moves use checked absolute paths with long-path support; the remaining merge is confined through os.Root. Existing regular files win. Private staging and temporarily relaxed read-only directory modes are cleaned up/restored. These guarantees target trusted runner filesystems, not hostile concurrent writers.

Directory/root preparation remains ordered. `cache-restore-concurrency` bounds independent per-file publication afterward (default four, range 1-16). Workers have private counters and 32 KiB fallback-copy buffers; all workers join before temporary staging is removed or directory modes are restored. Set it to 1 for sequential publication. Tar validation, staging and missing-tree publication remain sequential, and this limit does not multiply download/chunk workers. Tree publication reduces filesystem operations without changing worker defaults.

Whole-archive saves walk and pack the cache into a temporary file. Uncompressed tar output uses a bounded 256 KiB buffer; close/flush failures prevent upload. In split mode, a restored module tree is first fingerprinted by paths, permissions and full file contents, ignoring timestamps. Equal content skips packing and upload; changed modules pay the check plus packing. Build snapshots remain fresh by default. In split layout, `cache-build-save: false` skips build packing and transfer before filesystem access, without changing restore policy or cache identities. A workflow expression can gate these saves by run number; no remote save timestamp is inferred. This trades repeated upload avoidance against local reads, CPU, temporary disk and cache entry growth.

Whole-archive gzip packs use `cache-compression-concurrency` (default four, range 1-16). Fixed 4 MiB raw-tar blocks are compressed with the standard gzip level by default and written in order as concatenated gzip members. Worker count and input write sizes do not change encoded bytes. Existing gzip readers accept the continuous tar stream; cache compatibility namespaces are unchanged. Concurrency 1 compresses these same fixed members sequentially. `cache-gzip-level` optionally selects levels 1 through 9 for both archive and chunk compression. The default retains existing bytes; all levels use existing gzip readers and archive namespaces. Changing level can change newly encoded chunk hashes, while previously verified chunks remain reusable. Member boundaries can affect compression ratio relative to the older single-member stream, so record encoded size as well as elapsed time.

Submitted blocks are bounded until ordered output completes, avoiding an unbounded reorder queue behind a slow block or destination. Steady retained payload capacity is approximately 12 MiB per worker plus one 4 MiB producer block (52 MiB at four workers). Buffer growth, garbage collection, codec state and normal runtime overhead can increase memory beyond that allowance; it is not a peak-memory or resident-memory guarantee. Failed or cancelled packing joins workers before returning. This compression pool is unused for uncompressed archives and for chunked packing, whose separate chunk workers perform compression.

Zstd uses the bundled, pinned `github.com/klauspost/compress/zstd` implementation with its default speed level, checksummed dictionary-free frames, and a 4 MiB window. Whole-archive saves use `cache-compression-concurrency`; parallel encoding uses bounded ordered jobs of 16 MiB plus overlap and codec/output buffers. This has a different memory cost from the gzip block pool above. Concurrency 1 encodes synchronously. Restore uses one decoder worker, low-memory mode, a 4 MiB maximum window, and an 8 MiB decoder memory option, with whole-buffer decoding disabled. Those settings are codec limits, not a process-memory ceiling; the expanded tar byte limit independently bounds streamed output. Invalid checksums, truncated streams, excessive windows, and trailing garbage fail before publication. Zstd has its own compression namespace; gzip/none identities are unchanged.

Archive packing, restore and module fingerprinting independently cap metadata at 250,000 visited entries, 128 MiB of cumulative path-prefix bytes and 128 path components including the cache root. Each entry charges its full name and every ancestor prefix, including repeated prefixes, to bound implicit-directory work without another retained index. Restore additionally caps cumulative nonstandard PAX/xattr and owner/link string bytes at 16 MiB, and drops unused header strings/maps before retaining entries. Standard PAX paths are already charged to the path budget; parsed numeric/time fields have fixed-size storage. These are logical safety budgets, not process-memory ceilings: filesystem directory enumeration, tar parsing and runtime overhead can retain additional memory. Rejection happens before restore publication; packing/fingerprinting failures prevent a save. Existing accepted archive bytes, content digests and cache namespaces are unchanged, but previously accepted snapshots exceeding a metadata budget now fail under the configured cache error policy. Source changes require a newly packaged distribution.

## Optional chunked storage

`cache-storage: chunked` splits the uncompressed deterministic tar into content-defined chunks of 1–8 MiB, approximately 4 MiB target. Each chunk is compressed independently when gzip or zstd is selected. Missing immutable chunks are uploaded before publishing a fresh manifest. The same GitHub cache service and credentials are used; no additional consumer action or infrastructure is required.

After a fully validated chunked restore, private main/post state retains at most 1,024 raw-content SHA-256 to encoded-reference hints per snapshot. Save hashes complete current raw chunks and checks exact remote existence before reusing a hint, bypassing compression on a hit. Eviction falls back to normal encoding and publication. Hints contain only hashes and sizes, never credentials or signed URLs; they do not change the v1 manifest or chunk identities. Cold/write-only saves and chunks beyond the hint bound still use normal compression and lookup. Hints add raw-content hashing on restore and hinted saves; their total workflow benefit is unmeasured. Tar timestamps remain intact, including Go build-cache ages.

Chunk workers perform save hash/compression/lookup/upload and restore lookup/download/decompression. Each save worker reuses its own gzip or zstd encoder and output buffer only after the previous chunk operation finishes; retained codec buffers scale with the configured worker count rather than the number of chunks. Resetting an encoder preserves the encoded bytes and content-addressed keys for the pinned codec profile; future codec upgrades can change encoded chunk identities. Duplicate chunks in one snapshot transfer once. Every referenced chunk is checksum-verified. Restore writes validated offsets in a private archive, then validates the complete archive before merge. Missing/evicted referenced chunks produce a cache miss; corruption follows the configured error policy. Chunked and whole-archive namespaces are separate, and default reuse does not cross jobs or architectures. Opt-in `cache-module-scope` shares only split module snapshots across jobs/workflows/compiler versions within a repository, retaining OS/architecture/storage/codec partitions. Build snapshots keep their existing identities; the [security model](SECURITY_MODEL.md) defines the shared-writer trust boundary.

`cache-chunk-concurrency` independently bounds chunk workers. Chunk blob operations use one upload/download worker each, avoiding nested request multiplication. Allow approximately 32 MiB of chunk buffers per active worker plus 16 MiB for the save producer: about 144 MiB at the default four workers, excluding codec/runtime overhead. This is a planning allowance, not a total memory measurement. There is no unbounded payload queue or restore reorder buffer.

Chunking still scans/packs the complete tree and retains a full temporary uncompressed tar on save/restore. It can avoid repeated encoded transfers, while adding manifests, lookups, requests, buffers and independently evictable entries. Neither chunking, parallelism nor compression is universally preferable. [Benchmark methodology](BENCHMARKS.md) defines the measurements; [the roadmap](../ROADMAP.md) records deferred alternatives.
